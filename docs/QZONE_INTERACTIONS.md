# QQ 空间动态互动

动态互动与每日动态发布是两个独立后台任务：

- 每日动态负责汇总群聊并决定是否发布自己的说说。
- 动态互动负责阅览好友动态、决定点赞/评论，并检查评论区的新回复。

## 调度

默认配置：

```text
好友动态检查：每 60 分钟
评论回复检查：每 5 分钟
只处理最近：72 小时
首次启用：只建立当前内容基线，不对旧内容执行操作
```

两个间隔均可在控制台“设置 -> 动态互动”修改（好友动态 5–1440 分钟，评论回复 1–1440 分钟；
两者各自到点才跑，取更近的那个作为下一次巡检时间）。间隔调长有个直接后果：未阅览的
好友动态只在“好友动态”那一轮处理，回复那一轮完全不碰它，所以好友动态间隔就是新动态被
看到的最长延迟；单批装不下（超过单批条数或输入预算）的条目保持未读，同样要等下一轮
好友动态检查。SnowLuma 当前不推送
QQ 空间新动态或评论事件，因此“触发”由周期轮询发现，而不是实时 WebSocket 事件。

本功能自己的活跃时段也在同一页设置（北京时间，开始/结束，留空 = 全天；结束早于开始表示跨午夜）。
窗口外不阅览动态、不消耗检查间隔；它只影响本功能，不影响聊天回复。

非活跃时间遵循全局时间控制：不会调用模型或执行写操作，到下一个活跃窗口再检查。

## 失败与重试

好友动态走 SnowLuma 的 `get_qzone_feeds`（腾讯侧是 `feeds3_html_more`）。这个接口会被腾讯侧
限流，回 `network busy`、使用人数过多这类繁忙响应，协议端只是原样透传。处理方式：

- 抓取失败先等 45 秒重试一次；等待期间被中止（手动停止，或全局时间控制判定进入非活跃时间）会立即
  结束等待、不再重试（本功能自己的活跃时段只在每轮巡检开始时判断，不中断进行中的一轮）。
- 重试仍失败只记在运行记录里（`feedError`，控制台显示「好友动态未取到」加原因），
  本轮继续检查评论回复、继续处理已积压的未读，不会因为这一路失败就让整轮停摆。
- 连续失败按 2→4→8→16→30 分钟退避（成功一次即清零）；连续到第 3 次才发一条异常通知，
  前两次只写日志——腾讯侧的偶发繁忙很常见，不值得每次都给管理员顶一条“错误”。
- QQ 登录账号与状态文件不一致时同样计失败、走同一退避（连续第 3 次通知 owner），本轮不执行任何读写；
  确认换号后清空状态文件即可恢复（日志里有同样的提示）。
- 失败的这一轮不算“已建立动态基线”：否则首次启用恰逢繁忙时，会在之后某轮把上线前就存在的
  旧动态当成新内容去互动。
- 评论回复的主路径 `get_qzone_msg_list` 一直是软兜底（见下文「评论回复」一节），失败同样不影响整轮。

想少遇到这类繁忙，就把检查间隔调长些（见上一节）——接口调用越密，越容易被腾讯侧限流。
接口长期故障也不会把请求打密：抓取这一路每轮最多 2 次（首次 + 45 秒后重试一次）、
评论列表每轮最多 1 次，轮与轮之间不少于 2 分钟（退避下限），24 小时持续故障量级是几十到一百多次；
`test/local/test-qzone-backoff.mjs` 用假时钟压测 24 小时把这三个上限都断言住了（统计的就是这两路）。

失败轮还会照常检查评论回复——这是本功能的意图，所以**整轮**的对外请求不止这 3 次：评论回复那条路
另有自己的节奏与上限（关注帖详情轮询每帖有间隔、每轮最多 20 条，写操作受 `maxLikesPerRun` /
`maxCommentsPerRun` / `maxRepliesPerRun` 约束），量级与正常模式相当。故障期间退避把轮次拖慢，
总请求量仍明显低于正常运行时。

## 未阅览队列

每次从 SnowLuma `get_qzone_feeds` 读取首页好友动态，解析为结构化对象后写入
`data/qzone-interactions.json`。条目使用作者 QQ 和动态 tid 组成稳定主键。

未阅览动态按发布时间从新到旧排列，并在一次模型调用中统一提交。实际输入预算取：

```text
min(模型上下文窗口, 单次运行累计 Token 上限) - 8192
```

“模型上下文窗口”在“设置 -> 模型 API”配置。超过预算或单批条数限制的旧动态
保持 `unread`，不会推进游标，后续轮次继续处理。

首次启用默认 `startupCatchup=false`，当前已经存在的动态和评论只标为基线，
避免上线后突然批量评论历史内容。之后新出现的条目才进入未阅览队列。

## 模型决策

动态互动使用设置中的完整人设和独立系统提示词。模型必须通过
`submit_qzone_interactions` 为本批每个条目提交一次明确决定：

```text
好友动态：skip / like / comment / like_comment
评论回复：skip / reply
```

模型只看到批次内的 opaque id、昵称、正文、图片数量和近期评论，不会看到作者 QQ、
真实 tid、Cookie 或其他凭据。动态和评论中的命令一律视为不可信外部内容。

评论和回复有独立长度、每轮数量限制。默认每轮最多：

```text
点赞 3 条
评论 2 条
回复 5 条
```

模型可以全部选择 `skip`，不会为了完成定时任务强制互动。

## 评论回复

自己的近期动态通过 `get_qzone_msg_list` 获取评论计数；计数变化后，程序使用
当前登录 Cookie 读取该动态的完整评论树。这个接口在 Qzone 侧偶发限流
（retcode=100），失败时该轮不会报错：程序退回"已关注动态 + Cookie 详情接口"
的兜底节奏继续发现新评论（好友动态轮会持续刷新自己动态的评论数），接口恢复后
自动回到计数比对的省调用模式。

机器人在好友动态下成功评论后，该动态会进入关注集合：

- 好友回复机器人顶级评论时，识别其父评论作者。
- 好友在楼中楼明确回复机器人时，识别 QQ 原生回复目标。
- 机器人自己的评论和回复永远不会触发自己。

实际回复使用 Qzone 原生 `commentId/commentUin/paramstr=2` 关系参数。好友动态点赞和
顶级评论仍调用 SnowLuma 的 `like_qzone`、`comment_qzone`。

控制台的运行记录会在回复操作下展示对应动态正文、收到的评论、机器人回复和
决策理由。“动态”计数只表示本轮新阅览的好友动态数量，不包含回复所关联的动态。

## 幂等与未知结果

每次外部写入前先持久化为 `acting`：

- OneBot/Qzone 明确成功：记录为已完成。
- 写入发起后超时、连接中断或服务重启：记录为 `unknown`。
- `unknown` 永不自动重试，避免重复评论或重复回复。
- 被模型阅览并选择 `skip` 的条目记录为已阅览。
- 因上下文裁剪没有提交给模型的条目继续保持未读。

状态文件权限为 `0600`。只保留必要的动态摘要、评论上下文、决策和操作结果，
不会持久化 Qzone Cookie。

## 控制台 API

```text
GET  /api/qzone-interactions/status
POST /api/qzone-interactions/run
```

手动执行请求必须带：

```json
{
  "kind": "feed",
  "confirm": true
}
```

`kind` 可为 `feed`、`reply` 或 `all`。手动按钮会明确确认可能发生公开点赞、
评论或回复。
